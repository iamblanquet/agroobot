# Catálogos de supervisión

La lógica de grupos descrita abajo corresponde a la primera migración. Para la
versión actual aplicar también `20260918_predio_groups.sql` y consultar
`20260918_predio_groups.md`: los grupos pertenecen al predio y los proyectos se
asignan explícitamente a él.

Antes de desplegar esta versión con Supabase, ejecutar `20260918_catalogs.sql`
en el SQL Editor del proyecto correspondiente. La función solo permite ejecución
al rol de servicio del backend. No modifica registros existentes; alinea las
secuencias de predios y obras con los identificadores ya utilizados.

La API utiliza una llamada RPC para guardar predio, frente y vínculos en una
transacción. Si falta la función, la operación falla sin recurrir a escrituras
REST parciales. En SQLite utiliza la transacción local y no requiere migración.

Telegram se intenta después de confirmar los datos. Si no está disponible, la
API devuelve el registro guardado junto con `telegram_status: pendiente` y un
aviso. La acción de sincronización permite reintentar sin volver a crear el
predio o frente. Los IDs de tema existentes, incluidos 101 a 107, se conservan.
Para reemplazar un tema de pruebas, vaciar explícitamente su ID al editar y luego
usar la acción de crear tema.

Los intentos simultáneos de un mismo tema se agrupan dentro de un proceso. Esto
no garantiza exclusión entre múltiples instancias del servidor. Si Telegram
crea un tema pero falla el guardado de su ID, la respuesta informa el ID creado
para vincularlo manualmente antes de volver a sincronizar.

Validación local: `npm run test:catalogs` y `npm --prefix client run build`.
Las pruebas usan SQLite en memoria, Supabase simulado y un bot simulado: no
ejecutan la migración contra un servidor PostgreSQL ni envían mensajes reales.
